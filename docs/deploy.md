# Deploying the hosted demo

A public demo on free plans only: no credit card, nothing that expires. It takes about fifteen minutes and three accounts.

| Piece | Where | Why there |
| --- | --- | --- |
| Web client | Vercel (Hobby) | Built for Next.js; free for personal projects |
| API, worker, payment simulator | Render (free web service) | Runs a Docker image as is |
| Redis | Render Key Value (free) | No command quota, which matters because workers poll |
| Postgres | Neon (free) | Does not expire. Render's free Postgres is deleted after 30 days |

> Free plans change. These steps were followed in November 2026 to put up [lobbyd.vercel.app](https://lobbyd.vercel.app). If a step no longer matches what you see, the provider changed it.
>
> One thing differed from the plan: a Neon account that was created through Vercel can only add databases from Vercel's **Storage** tab (Create Database, Neon), not from the Neon console. Use the `DATABASE_URL_UNPOOLED` value it gives you.

## What is different about the demo

The real deployment is three processes, as in `docker-compose.yml`. A free plan gives one small web service and no background workers, so the demo runs all three in one process ([`apps/demo`](../apps/demo/src/lobbyd_demo/main.py)): the worker's loops run as tasks beside the API, and the payment simulator is mounted in memory. It is the same code, wired the way the test suite wires it.

On every start it applies migrations and, if the data is missing or more than a day old, wipes and reseeds. Free services sleep after fifteen minutes without traffic, so in practice the demo resets itself daily and always shows upcoming tournaments.

Limits to know about:

- **Cold starts.** The first request after a sleep takes up to a minute while the service wakes. The page may show an error once; reload.
- **Small.** A fraction of a CPU and about 512 MB of memory. Fine for clicking around, not for the load tests.
- **Redis is memory only.** If Render restarts it, events that were published but not yet handled are lost. Payments recover by themselves (the worker polls the provider for ones that went quiet); a confirmation email might not be recorded. Acceptable for a demo, and the reason production Redis has persistence turned on.

## 1. Postgres on Neon

1. Create a project at neon.com. Any region; pick the one closest to the Render region you will use.
2. On the project dashboard, open **Connect**, turn **Connection pooling off**, and copy the connection string. It looks like `postgresql://user:password@ep-something.region.aws.neon.tech/neondb?sslmode=require`.

Use the direct string, not the pooled one: the pooler runs in transaction mode, which does not work with the prepared statements this app's driver uses. The app accepts the string exactly as Neon gives it.

## 2. API and Redis on Render

1. At render.com choose **New > Blueprint** and pick your fork of this repository. Render reads [`render.yaml`](../render.yaml) and proposes one web service and one Key Value instance.
2. It asks for one value, `LOBBYD_DATABASE_URL`. Paste the Neon string. The three secrets are generated by Render.
3. Apply. The first build takes a few minutes. When it is live, open `https://<your-service>.onrender.com/readyz`: it should say `"status":"ok"`. The API docs are at `/docs`.

## 3. Web client on Vercel

1. At vercel.com choose **Add New > Project** and import the repository.
2. Set **Root Directory** to `apps/web`. Leave "Include files outside the root directory" on: the client imports its API types from `libs/api-client`.
3. Add two environment variables, using your Render address:

   | Name | Value |
   | --- | --- |
   | `LOBBYD_API_URL` | `https://<your-service>.onrender.com` |
   | `NEXT_PUBLIC_LOBBYD_WS_URL` | `wss://<your-service>.onrender.com` |

4. Deploy, then open the site. Sign in with the demo accounts:

   | Role | Email | Password |
   | --- | --- | --- |
   | Buyer | `buyer@example.com` | `buyer-demo-password` |
   | Organizer | `organizer@example.com` | `organizer-demo-password` |

These passwords are public on purpose. The demo holds no real data and erases itself.

## Switching the assistant on

Optional. Without it the assistant page says it is off and everything else works.

1. Create a free API key at Google AI Studio (aistudio.google.com, **Get API key**). No card is needed.
2. In Render, open the `lobbyd-api` service, **Environment**, and set `LOBBYD_ASSISTANT_API_KEY` to that key. The base URL and model are already set by the blueprint; on a service created before they were added, also set `LOBBYD_ASSISTANT_BASE_URL` to `https://generativelanguage.googleapis.com/v1beta/openai` and `LOBBYD_ASSISTANT_MODEL` to `gemini-3.5-flash-lite`.
3. Save. Render redeploys, and the Assistant page starts answering.

The free quota is small. A daily ceiling (`LOBBYD_ASSISTANT_DAILY_TURNS`, 150) keeps the demo inside it; past that the assistant says it is busy until tomorrow.

## After it is up

- Put the Vercel address at the top of the README.
- To reset by hand, restart the Render service after emptying the `users` table, or wait a day.
- Metrics are at `/metrics` on the API. Grafana and Jaeger are part of the local stack, not the hosted demo (see [observability](observability.md)).

## A real deployment

The demo is not the production shape. For that: run the API, the worker, and migrations as separate processes from the same image (as Compose does), give the API two or more instances behind a load balancer, turn Redis persistence on, set `LOBBYD_TICKET_SIGNING_KEY` and the other secrets from a secret manager, and replace the payment simulator with a real provider behind the `PaymentProvider` interface. [Scaling](scaling.md) covers what comes after that.
